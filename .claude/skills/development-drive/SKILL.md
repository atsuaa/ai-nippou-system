# development-drive スキル

このスキルはメインエージェントが直接使用する。issue単位で`programmer → tester → reviewer`のパイプラインを回し、reviewerによるマージ完了(OK判断)をゴールとする。実装・テスト・レビューはすべてサブエージェントに委ね、メインエージェントはオーケストレーションと人への確認判断のみを担う。

## 対象issueの確認

- 処理対象issueの番号を明確にする。複数issueをまとめて依頼された場合、「並列で進めてよいか」をユーザーの指示から判断する。明示的に並列指示がある場合のみ並列処理し、それ以外は1つずつ順番に処理する。
- 各issueについて`gh issue view <issue番号>`で内容を確認し、以降のサブエージェント依頼文に反映する。

## 1. programmerへ実装依頼

Agentツールで`programmer`サブエージェントを呼び出す。promptには以下を含める。

- issue番号と要件概要、関連する`docs/requirements.md`のFR番号・`docs/screens.md`のSC番号・`docs/api.md`のAPIエンドポイント
- 「実装完了後はprogrammer-git-workflowスキルに従いPRを作成し、PR番号を報告してください」という指示

worktreeの扱い:

- **並列実行の指示がある場合のみ**、promptに「他のissueと並行して作業するため、git worktreeを使って実装してください」と明示的に含める。
- **単独issueの場合はworktreeについて一切言及しない。** programmer自身がprogrammer-git-workflowスキルに従い通常のブランチ運用を選ぶ。
- 並列実行時は複数issueのprogrammer呼び出しを`run_in_background: true`で並行して投げてよい。単独issueの場合も、結果を待って次のフェーズに進む必要があるためbackgroundで実行し、完了通知を待つ。

programmerからPR番号を含む完了報告を受け取ったら手順2へ進む。

## 2. testerへテスト依頼

programmer完了報告のPR番号を使い、`tester`サブエージェントを呼び出す。promptに「PR #<番号>をtest-executionスキルのモード1(PR指定)でテストし、結果をPRにコメントしてください」を含める。

tester完了報告の結論に応じて分岐する。

- **合格** → 手順3(reviewerへ依頼)へ進む。
- **要修正** → 手順4(programmerへの差し戻し)を行い、修正完了後に手順2からやり直す。**この場合reviewerには回さない。**
- **判定不可**(「検討事項」に依存) → 作業を中断し、ユーザーに確認する。

## 3. reviewerへレビュー依頼

testerが合格と判定したPRについて、`reviewer`サブエージェントを呼び出す。promptに「PR #<番号>をpr-reviewスキルに従ってレビューしてください」を含める。

reviewer完了報告に応じて分岐する。reviewerはpr-reviewスキルに従いマージ完了時に対応issueのクローズまで行う。issue番号が特定できずクローズされなかった場合は、メインエージェントが`gh issue view`等でissue番号を確認した上で`gh issue close`を行う。

- **マージ完了** → issueがクローズされたことを確認する。このissueのパイプラインは完了。次のissueがあれば手順1に戻る。
- **マージ見送り(要修正)** → 手順4(programmerへの差し戻し)を行い、修正完了後に手順2(tester)からやり直す。
- **マージ見送り(tester未検証)** → 通常このフローでは発生しないはずだが、発生した場合は手順2に戻ってtesterへ依頼し直す。
- **判定不可**(「検討事項」に依存) → 作業を中断し、ユーザーに確認する。

## 4. programmerへの差し戻し

- testerまたはreviewerからの指摘内容(具体的な問題点・ファイルパス・行番号)を要約せずそのまま`programmer`サブエージェントに伝え、「PR #<番号>のブランチに対して以下を修正し、同じブランチにコミット・pushしてください」という形で依頼する。新しいPRは作らない。
- 修正完了報告を受けたら、指摘元に応じて手順2(testerからの差し戻し)または手順2(reviewerからの差し戻しも再度testerから検証しなおす)に戻る。
- **同一issueで同種の指摘による差し戻しが2回以上発生した場合**、無限ループを避けるため作業を中断し、状況をユーザーに報告して判断を求める。

## 人の判断が必要な場合(中断基準)

以下に該当する場合、パイプラインを中断し、AskUserQuestionまたは通常の応答でユーザーに確認を取る。自己判断で仕様を補ったり、差し戻しを繰り返し続けたりしない。

- tester/reviewerが「検討事項」に依存する判定不可を出した場合
- programmerが仕様不明でユーザーへの確認が必要と報告した場合
- 同一issueで同種の指摘による差し戻しが2回以上続いた場合
- サブエージェントがエラーで完了報告を返せなかった場合(CI環境不備、権限エラーなど)
- マージ後に重大な問題が発覚した場合など、想定外の事態が起きた場合

## 進行状況の報告

- 各issueについて、どのフェーズ(実装中/テスト中/レビュー中/差し戻し/完了)にあるかをユーザーに簡潔に報告する。
- 複数issueを並列処理している場合、全体の進行状況を一覧できる形で報告する。

## 禁止事項

- testerが「要修正」または「判定不可」の判定を出したPRを、そのままreviewerに回さない。
- 差し戻しのループが解消しないまま繰り返し続けない(2回以上で必ず中断する)。
- 並列実行の指示がないのに複数issueを並行して進めない。逆に並列実行の指示があるのにworktreeを使わせない。
- 「検討事項」に依存する判断をメインエージェント自身が代わりに決めてしまわない。
