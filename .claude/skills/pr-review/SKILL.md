# pr-review スキル

reviewerサブエージェントがPRレビューを行う際は、この手順に従うこと。マージはmainブランチの共有状態を変更する重大な操作であるため、判断基準を満たさない限りマージしないことを最優先する。

## 1. レビュー対象PRの取得

1. `gh pr view <PR番号>` でPRのタイトル・本文・対象ブランチ・変更ファイル一覧を確認する。
2. `gh pr diff <PR番号>` で実際の差分を確認する。
3. PR本文やリンクされたissueから、対応するFR番号・SC番号・APIエンドポイントを特定する。特定できない場合、`docs/requirements.md`等を参照して該当箇所を推定する。あわせて、対応するissue番号をここで確定させておく(手順5でマージ後にクローズする際に使う)。

## 2. 仕様との整合性確認

- 差分の内容が、特定した仕様(`docs/requirements.md` / `docs/screens.md` / `docs/api.md`)と整合しているかを確認する。
- `CLAUDE.md`の「維持すべきアーキテクチャ判断」から逸脱していないかを確認する。
- 「検討事項」として未確定な仕様に対して、PRが独自の解釈で実装を確定させてしまっている場合は問題点として扱う。

## 3. testerの検証コメントの確認

1. `gh pr view <PR番号> --comments` (または `gh api repos/{owner}/{repo}/issues/{PR番号}/comments`)でPRに投稿されたコメント一覧を取得する。
2. tester.mdの報告フォーマット(「結論」「確認した項目」「問題点」「不足しているテストケース」「判定不可の項目」といった見出しを含むコメント)に該当するものを、testerサブエージェントによる検証コメントとして識別する。
3. 該当コメントが**存在しない場合**: tester未検証と判断し、マージしない(手順5へ)。
4. 該当コメントが**存在する場合**: その結論を確認する。
   - 「合格」であれば次に進む。
   - 「要修正」や「判定不可」であれば、その指摘事項が解消されているかを差分から確認する。解消されていなければ問題点として扱う。

## 4. CI状態の確認

- `gh pr checks <PR番号>` でCI(lint/test/build)がすべて成功しているかを確認する。
- 失敗しているチェックがある場合、または`gh pr view <PR番号>`でマージ可能性(mergeable状態)がコンフリクトを示している場合は、それ自体を問題点として扱い、マージしない。

## 5. マージ判断とコメント投稿

判断結果に応じて、以下のいずれかを行う。

### A. マージする場合(以下すべてを満たす場合のみ)

- 仕様との整合性に問題がない
- testerの検証コメントが存在し、その結論が「合格」(または指摘事項がすべて解消済み)
- CIがすべて成功しており、コンフリクトがない

手順:
1. `gh pr comment <PR番号> --body "..."` でレビュー結果(reviewer.mdの報告フォーマットに従う)を投稿する。
2. `gh pr merge <PR番号> --squash` でマージする(リポジトリのマージ方式について特段の指定がない限りsquashを既定とする)。
3. マージ後、`gh pr view <PR番号>`でマージが完了したことを確認する。
4. 手順1で対応するissue番号を確定できている場合、`gh issue close <issue番号> --comment "PR #<PR番号>をマージして対応完了しました。"`でissueをクローズする。issue番号が特定できない場合はクローズを行わず、その旨をユーザーへの報告に明記する。

### B. マージしない場合

以下のいずれかに該当する場合はマージせず、`gh pr comment <PR番号> --body "..."`で問題点・見送り理由を具体的にコメントする。

- testerの検証コメントが存在しない → 「tester未検証のためマージを見送る」旨と、テスト実施を依頼する旨をコメントする。
- 仕様との不整合、アーキテクチャ判断からの逸脱がある → 該当箇所(ファイルパス・行番号)と期待される仕様を具体的に指摘する。
- testerの指摘事項が未解消 → 未解消の指摘内容を引用しつつ、対応が必要な旨を伝える。
- CI失敗・コンフリクトがある → その状態を指摘する。
- 未確定事項(検討事項)に依存して判断できない → 依存する検討事項を明記し、判定不可であることを伝える。

## コメント・マージ時の注意

- PRへのコメント・マージは他者にも見える公開アクションであり、mainブランチの共有状態を変更する。判断基準を厳格に適用し、迷いがある場合は安全側(マージしない)に倒す。
- コメント本文はHEREDOCで渡し、日本語でreviewer.mdの報告フォーマットに従う。
- マージ後にコードを修正することはしない。修正が必要な問題を見つけた場合は、必ずマージ前にコメントで指摘する。

## 禁止事項

- testerの検証コメントを確認せずにマージしない。
- CIが失敗している、またはコンフリクトが残っているPRをマージしない。
- 未確定事項を独自に解釈して「仕様通り」と判断しない。
- マージ後に問題が発覚した場合でも、reviewer自身が修正コミットを作成しない(programmerサブエージェントに委ねる)。
