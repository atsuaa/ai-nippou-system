# test-execution スキル

testerサブエージェントがテストを実施する際は、依頼内容がどのモードに該当するかをまず判定し、モードごとの手順に従うこと。検証プロセスや報告フォーマットそのものはtester.mdの本体指示に従い、このスキルは「何を対象に検証するか」と「結果をどこに返すか」を規定する。

## モードの判定

- 依頼にPR番号(またはPRのURL)が含まれる → **モード1: PR指定**
- 依頼にissue番号(またはissueのURL)が含まれる → **モード2: issue指定**
- どちらも含まれない → **モード3: 指定なし(現在の作業ツリー)**

## モード1: PR指定

1. `gh pr view <PR番号>` でPRのタイトル・本文・対象ブランチ・差分ファイルを確認する。
2. 現在の作業ツリーに未コミットの変更がないか`git status`で確認する。変更が残っている場合はチェックアウトせず、ユーザーに報告する(勝手にstash/破棄しない)。
3. 問題なければ`gh pr checkout <PR番号>`でPRブランチをローカルにチェックアウトする。
4. `gh pr diff <PR番号>`で差分を確認しつつ、tester.mdの検証プロセス(要件・仕様との整合性確認、`npm run lint`/`npm run test`/`npm run build`の実行、エッジケースの洗い出し、権限マトリクスとの整合性確認)に従って検証する。
5. 検証結果をtester.mdの報告フォーマット(結論/確認した項目/問題点/不足しているテストケース/判定不可の項目)に沿ってまとめ、`gh pr comment <PR番号> --body "..."`で投稿する。コメント本文はHEREDOCで渡し、整形を崩さないようにする。
6. 検証完了後、元にいたブランチへ戻す(`git checkout <元のブランチ>`)。

## モード2: issue指定

1. `gh issue view <issue番号>` でissueの内容(要件・受け入れ基準)を確認する。
2. そのissueに対応する実装を特定する。
   - `gh issue view <issue番号>`の出力や関連PRのリンクから、対応するPRが既にあるか確認する。対応するPRが見つかった場合は、モード1の手順2〜4と同様にそのPRブランチをチェックアウトして検証する。
   - 対応するPRが見当たらない場合、現在の作業ツリーの差分(`git diff`/`git status`)がそのissueに対応する実装であるとみなし、issueの要件・受け入れ基準に対して通常の検証プロセスを行う。
3. 検証結果をtester.mdの報告フォーマットに沿ってまとめ、`gh issue comment <issue番号> --body "..."`で投稿する。
4. ブランチを切り替えていた場合、検証完了後に元のブランチへ戻す。

## モード3: 指定なし(現在の作業ツリー)

- tester.mdの通常フロー(`git diff`/`git status`で差分を把握し、対応する要件・画面・APIを特定して検証する)に従う。
- この場合はPR/issueへのコメント投稿は行わず、通常の報告フォーマットでユーザーに直接結果を返す。

## コメント投稿時の注意

- PR/issueへのコメントは他者にも見える公開アクションである。投稿前に検証結果の内容を確定させ、憶測や未確定事項を断定的な結論として書かないこと。「検討事項」に依存して判定不可の場合はその旨を明記する。
- コメント本文は日本語で、tester.mdの報告フォーマットに従う。
- モード1・モード2でブランチを切り替えた場合、コメント投稿の有無にかかわらず検証完了後に必ず元のブランチへ戻す。

## 禁止事項

- PR/issueが指定されていない(モード3)のに、誤ってPR/issueへコメントを投稿しない。
- 検証中にコードの修正やコミットを行わない(testerは検証専任であり、実装はprogrammerサブエージェントの役割)。
- ブランチ切り替え時、ローカルの未コミット変更を確認せずに`checkout`やstashで上書き・破棄しない。
